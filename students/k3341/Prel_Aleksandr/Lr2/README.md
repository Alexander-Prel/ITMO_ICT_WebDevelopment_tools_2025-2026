## Установка

Проверенная среда: Python 3.12.13, macOS 15.3 ARM64, PostgreSQL 16.
Выполнить из папки `Lr2`:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
export PYTHONPATH="../Lr1"
```

В PowerShell вместо `source` и `export` используются
`.venv\Scripts\Activate.ps1` и `$env:PYTHONPATH="../Lr1"`.
Переменная `PYTHONPATH` нужна для импорта `app` из ЛР1, она действует только
в текущем терминале. В PyCharm: рабочая папка `Lr2`, интерпретатор её `.venv`,
в переменных запуска `PYTHONPATH=../Lr1`, запуск по имени модуля, не по пути файла.

Для суммирования база не нужна. Для парсинга предварительно создать PostgreSQL
пользователя и базу по инструкции ЛР1. Если `Lr1/.env` ещё нет, создать его
из `Lr1/.env.example`, указать свой `DB_URL` и случайный `SECRET_KEY`.
Не заменять существующий `.env` и не публиковать пароли. Конфигурация приложения
читает файл именно из `Lr1`, независимо от текущей рабочей папки.

Затем применить миграции в уже активированном окружении:

```bash
cd ../Lr1
python -m alembic upgrade head
cd ../Lr2
```

По умолчанию используется схема `public`. Переменную `LAB2_DB_SCHEMA` для
обычного запуска устанавливать не требуется. Парсер не создаёт таблицы
самостоятельно: `prepare_database()` проверяет таблицу и создаёт технического
импортера при его отсутствии.

## Задача 1: сумма

Короткая проверка трёх реализаций; ожидаемый ответ каждой программы: `55`.
Эти запуски **не являются** измерением полного задания:

```bash
python -m lab2.task1.threading_sum --n 10 --workers 3
python -m lab2.task1.multiprocessing_sum --n 10 --workers 3
python -m lab2.task1.async_sum --n 10 --workers 3
```

Текущий эксперимент перебирает каждое число от 1 до `10^10`. Не запускать
второй экземпляр, если первый ещё работает. Команда воспроизведения последовательно
измеряет threading, multiprocessing и asyncio; имя результата должно быть новым:

```bash
python -u -m lab2.task1.benchmark --n 10000000000 --workers 4 --repeats 1 --allow-long-run --output lab2/results/cpu_n1e10_new.json
```

Без `--allow-long-run` значения больше `100000000` отклоняются. Это защита
от случайного запуска. По умолчанию в коде по-прежнему `n=10^13`, поэтому
для нового опыта важно явно передавать `--n 10000000000`.
`calculate_sum()` есть в каждом из трёх модулей. Формула суммы используется
только для проверки результата **после** остановки таймера, не вместо цикла.

Файл результата появляется после первого завершённого прохода. Внутри прохода
процент и промежуточная сумма не сохраняются; продолжения с середины нет.
Для выбранного опыта JSON содержит `n=10000000000`, `full_assignment=false`.
Сравнивать завершённые результаты можно, когда `complete=true` и присутствуют
все три подхода с суммой `50000000005000000000`. Это не результат для `10^13`.
Полное условие проверяется отдельно: `n=10000000000000`, `full_assignment=true`,
`complete=true`. Существующий файл CPU benchmark не перезаписывает: для нового
опыта нужно новое имя. Уменьшенный диапазон не записывается в `cpu_full.json`.

## Задача 2: парсинг

В `lab2/task2/urls.txt` шесть адресов с двух сайтов. В `one_url.txt` один адрес
для проверки настройки. Адреса в файлах записываются обычным текстом, по одному
на строку, без Markdown-скобок.

```bash
python -m lab2.task2.threading_parser --urls lab2/task2/one_url.txt --workers 1
python -m lab2.task2.threading_parser --workers 3
python -m lab2.task2.multiprocessing_parser --workers 3
python -m lab2.task2.async_parser --workers 3
```

Каждая программа печатает по JSON-строке на URL и итоговое время. `ok=true`
означает успешную загрузку, разбор и фиксацию транзакции. `page_id` относится
к `parsed_pages`, `book_id` к `books`; значения ID зависят от состояния базы.
Для страниц цитат `book_id=null` допустим: у них нет карточки книги.
Итоговый `successful` при стандартном списке должен быть `6`.

Сравнение с прогревом и тремя повторами:

```bash
python -m lab2.task2.benchmark --workers 3 --repeats 3 --output lab2/results/io_new_run.json
```

Выбирать **новое имя** результата: в отличие от CPU benchmark, I/O benchmark
перезаписывает существующий файл. Не затирать `student_io_20260909_01.json`.
Один запуск делает 60 загрузок: 6 в прогреве и 54 в измеренных проходах.
Порядок подходов меняется между повторами; пауза между проходами не измеряется.
При ошибке страницы CLI возвращает ненулевой код, а benchmark не записывает
успешный итог сравнения. Уже успешно сохранённые страницы при этом остаются в БД.

## Проверка данных в PostgreSQL

В DataGrip открыть SQL-консоль подключения к базе из `Lr1/.env` и выполнить:

```sql
SELECT p.id, p.url, p.title, p.book_id, b.title AS book_title,
       p.fetched_at AT TIME ZONE 'Europe/Moscow' AS fetched_at_msk
FROM public.parsed_pages AS p
LEFT JOIN public.books AS b ON b.id = p.book_id
WHERE p.url IN (
  'https://books.toscrape.com/catalogue/a-light-in-the-attic_1000/index.html',
  'https://books.toscrape.com/catalogue/tipping-the-velvet_999/index.html',
  'https://books.toscrape.com/catalogue/soumission_998/index.html',
  'https://quotes.toscrape.com/',
  'https://quotes.toscrape.com/page/2/',
  'https://quotes.toscrape.com/page/3/'
)
ORDER BY p.url;
```

После успешного стандартного прохода ожидаются шесть источников и три связи
с книгами. При повторе сохраняются те же `page_id` и `book_id`, обновляются
заголовок источника и `fetched_at`. Ранее созданная карточка книги не изменяется.
`library_items` и заявки обмена парсер не создаёт и не редактирует.

Значения времени хранятся как timezone-aware UTC; запрос явно показывает
московское представление. SQL только читает данные, очистка рабочей базы не нужна.
