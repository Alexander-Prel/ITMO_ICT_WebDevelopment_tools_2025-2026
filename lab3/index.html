    Лабораторная работа 3¶

    Выполнил: Прель Александр, K3341. Дата отчёта: 21 сентября 2026.

    Тема: упаковка FastAPI в Docker, взаимодействие с источником данных по HTTP и выполнение задач через очередь. Основа — BookCrossing API из ЛР1 и парсер учебных сайтов из ЛР2. Условие: раздел «Лабораторная работа 3» в репозитории курса.

    Цель¶

    Разделить получение данных и их сохранение между сервисами, собрать их в Docker Compose и реализовать два способа запуска обработки: с ожиданием HTTP-ответа и через Celery с последующим получением результата по идентификатору задачи.

    Обязательная часть задания Реализация
    Контейнеризация API, БД и парсера Два Dockerfile, PostgreSQL и Compose
    HTTP-интерфейс парсера Отдельный сервис, POST /parse
    Вызов парсера из основного API POST /parser/parse, ожидание результата и сохранение
    Очередь Celery + Redis Отдельный worker, брокер и backend результатов
    Фоновый запуск из API POST /parser/parse/async, ответ 202 и task_id
    Проверка результата GET /parser/tasks/{task_id}

    Реализованы все три обязательные подзадачи. Периодические задачи и Celery beat не добавлены: в условии они выделены как дополнительная возможность. Установка и демонстрация, исходники и Docker-конфигурация.

    Архитектура¶

    Сервис Назначение
    api Существующие маршруты BookCrossing, JWT и новые маршруты парсинга
    parser HTTP-сервис загрузки и разбора HTML без доступа к БД
    db PostgreSQL, база bookcrossing_lab3
    redis Брокер Celery и backend результатов
    worker Обработка очереди, HTTP-вызов парсера и запись в PostgreSQL
    migrate Одноразовое применение миграций Alembic перед API и worker

    Пять сервисов работают постоянно. migrate после успешного выполнения завершается с кодом 0. Контейнеры обращаются друг к другу по именам сервисов. Для доступа с компьютера основной API использует порт 8003, парсер — 8004, PostgreSQL — 5433. Эти порты привязаны к 127.0.0.1; Redis не публикует порт.

    Стенд использует отдельное окружение Lr3/.env и отдельную БД. Локальная БД ЛР1 не является хранилищем ЛР3. Env-файлы не входят в образ; том PostgreSQL сохраняет данные между обычными остановками контейнеров.

    Папки сдачи Lr1, Lr2, Lr3 соседние. Сборка использует личную папку как контекст, .dockerignore разрешает только код и зависимости. API-образ содержит исходники всех трёх работ, а PYTHONPATH объединяет их Python-пакеты. Парсер получает только общий HTML-разбор ЛР2 и свой HTTP-код, без моделей БД. Оба приложения работают от непривилегированного пользователя.

    Реализация¶

    HTTP-парсер и сохранение¶

    lab3/parser_service.py принимает POST /parse с URL, загружает HTML учебного сайта и возвращает JSON по схеме PagePayload, соответствующей PageData из ЛР2. В нём нет транзакции PostgreSQL. Общий код lab3/service.py вызывает HTTP-парсер и передаёт результат в save_page из lab2/task2/database.py.

    Для каждой успешной страницы сохраняется источник parsed_pages: URL, заголовок, домен, время загрузки и необязательная связь с книгой. Книжная карточка Books to Scrape также создаёт запись books; страницы Quotes to Scrape дают источники без книги. Полные тексты цитат и описаний не импортируются. Карточки принадлежат техническому пользователю импортера. Физические экземпляры library_items не создаются.

    Один URL соответствует одному источнику. Уникальный индекс и транзакционная блокировка по URL защищают от одновременных дублирующих вставок. Повтор обновляет заголовок и время источника, сохраняя связь с существующей книгой. Название уже созданной книги не обновляется. Запись книги и источника выполняется в одной транзакции.

    Маршруты основного API¶

    Маршрут Поведение
    POST /parser/parse Ожидает парсинг и сохранение, возвращает ParseResult на основе Outcome
    POST /parser/parse/async Ставит задачу в очередь, возвращает 202, task_id, PENDING
    GET /parser/tasks/{task_id} Возвращает состояние, результат или ошибку задачи; неизвестный ID — 404
    GET /parser/pages Возвращает сохранённые источники

    Запуск защищён JWT существующего механизма авторизации BookCrossing. В отдельной БД ЛР3 пользователь сначала регистрируется через /auth/register и использует полученный токен. API ЛР3 сохраняет исходные маршруты управления книгами, экземплярами и обменами.

    Тело запросов запуска:

    {
  "url": "https://books.toscrape.com/catalogue/a-light-in-the-attic_1000/index.html"
}

    Синхронный результат содержит url, ok, title, page_id, book_id, error. Асинхронная задача после успешного завершения возвращает ту же информацию в поле result. 202 подтверждает принятие задания, а не завершённый импорт. Сбой HTTP-парсера в синхронном пути возвращает 502, сбой записи — 500. Ошибка выполнения Celery-задачи приводит к FAILURE и полю error. Недоступность Redis при постановке или чтении статуса даёт 503.

    Очередь¶

    API передаёт задачу в Redis. Worker получает её, вызывает тот же HTTP-парсер и общий код сохранения, затем помещает состояние и результат в backend Celery. Клиент получает результат отдельным запросом по task_id. Используются состояния PENDING, STARTED, SUCCESS, FAILURE. Маркер известной задачи хранится 24 часа с постановки, результат Celery — 24 часа после записи в backend. Несуществующий или истёкший ID возвращает 404; неверный формат UUID — 422. Статусы доступны авторизованным пользователям по ID, без отдельной проверки владельца. Список страниц общедоступен. Автоповтор парсинга после ошибки не включён.

    Синхронность HTTP-ответа отличается от Python async/await. Обработчик на async def также может держать HTTP-запрос открытым до полного результата. Celery переносит работу в отдельный worker; ранний ответ создаётся самой архитектурой маршрута и очереди. Это не обещает ускорения одной загрузки страницы. Конкурентность FastAPI, задачи и результаты Celery.

    Воспроизведение¶

    После настройки Docker команды запускаются из папки Lr3:

    bash setup.sh
bash compose.sh config --quiet
bash compose.sh up --build --wait --wait-timeout 180 -d
bash compose.sh ps -a
bash compose.sh logs --tail=80 migrate api worker

    Swagger основного API: http://127.0.0.1:8003/docs. setup.sh создаёт отдельный .env со случайными секретами, сохраняя существующий файл. Образы устанавливают зависимости независимо от локального .venv. Результаты контрольной проверки находятся в Lr3/results/. Для ручной демонстрации нужны регистрация, JWT, синхронный вызов, постановка асинхронной задачи, проверка её результата и просмотр источников в БД.

    Проверка и ограничения¶

    Проверка опубликованной структуры выполнена 21 сентября 2026 года. Контейнеры собраны из соседних папок Lr1/Lr2/Lr3. Для проверки использовались отдельные Docker volumes и внешние порты 18003, 18004, 15433; стандартные порты для запуска по инструкции остаются 8003, 8004, 5433.

    Тесты публикуемой копии 61 passed, 23 warnings
    Docker Compose и сборка двух образов Успешно
    Готовность сервисов api, parser, db, redis, worker: healthy
    Миграции Exit 0; 0004_timezone_aware_dates
    Синхронный импорт Источник и книга сохранены

    Страница цитат Источник без книги, book_id=null
    Проверка ошибок API 401 без JWT, 422 для запрещённого URL, 404 для неизвестного ID, 502 для несуществующей страницы

    Выполнено 24 HTTP-запросов сквозного сценария. Парсер обращался к настоящим учебным сайтам; Celery worker выполнял задачи, PostgreSQL сохраняла данные. После сценария сохранены два источника и одна связанная книга. ID относятся к этой проверочной базе и не обязаны совпадать на другом компьютере.

    Python в API-образе: 3.12.14; PostgreSQL использует Europe/Moscow. При остановленном worker постановка вернула 202 за 0.0077 с. Это время ответа о приёме, а не время парсинга. После запуска worker наблюдались состояния PENDING -> STARTED -> SUCCESS.

    Исходные результаты: HTTP-сценарий, очередь, техническая сводка.

    Проверки подтверждают работоспособность, а не сравнение производительности. Периодические задачи не включены. Доступ к статусу задачи не ограничен её автором сверх общей JWT-авторизации. Очередь не гарантирует ровно одно выполнение при любом отказе; повторное сохранение URL защищено транзакцией PostgreSQL. Состояния Celery не заменяют долговременные записи источников в БД.

    Вывод¶

    В реализации разделены HTTP-получение данных, сохранение в БД и выполнение заданий из очереди. Оба пути используют одну логику импорта, а различаются моментом ответа клиенту и исполнителем. Работа обоих путей подтверждена сквозной проверкой Docker-стенда, включая ошибки и повторный импорт без дублей.
